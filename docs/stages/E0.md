# E0. Каркас — что сделано и как это работает

Состояние на 2026-11-15, `main` = `feee606` (PR #1). Требования этапа — в `docs/TZ.md`, раздел «E0. Каркас».

E0 не добавляет ни одной функции анализа истории. Он даёт то, на чём строятся следующие этапы: workspace, бинарь `swhy` с двумя командами, фреймворк тестовых git-репозиториев, CI и место для замеров.

## Что можно запустить

| Команда | Что делает |
| --- | --- |
| `cargo run -p swhy-cli -- --version` | печатает `swhy 0.1.0` |
| `cargo run -p swhy-cli -- mcp` | поднимает MCP-сервер на stdin/stdout; список инструментов пуст |
| `cargo run -p swhy-fixtures -- list` | печатает имена fixture-репозиториев: `fx-rename`, `fx-smoke` |
| `cargo run -p swhy-fixtures -- build fx-rename` | собирает репозиторий и печатает `path=`, `head=`, `build=` |
| `eval/e0.sh` | собирает каждый fixture дважды и пишет `eval/results/E0-<дата>.json` |
| `cargo test --workspace` | 33 теста |

## Где что лежит

### `crates/swhy-core` — ядро

Библиотека, от которой зависят CLI, MCP и приложение.

- `src/model.rs` — единственный модуль с кодом. В нём типы из раздела ТЗ «Термины и модель данных»: `SymbolKey`, `SymbolSnapshot`, `Anchor`, `Event`, `EventKind`, `CommitType`, `Task`, `ProtectedLine`, `RegressionLink`, `TestLink` и вспомогательные. Все они сериализуются через serde и реализуют `Eq + Hash`. Перечисления пишутся в JSON в `snake_case` (`"body_changed"`, `"bugfix"`).
- `src/lib.rs` — объявляет модули и константу `VERSION`.
- Остальные файлы — `parse/`, `git/`, `track/`, `tracker/`, `tests/`, `classify.rs`, `protect.rs`, `chains.rs`, `guard.rs`, `response.rs`, `cache.rs`, `query.rs` — пустые: в каждом одна строка с номером этапа, который его наполнит. Они нужны, чтобы структура каталогов совпадала с ТЗ с первого дня.

Типы, которые ТЗ называет, но не определяет (`CommitId`, `TaskKey`, `Confidence`, `TestFramework`, `PathStep`, `Skeleton`), описаны в ADR-3.

### `crates/swhy-cli` — бинарь `swhy`

- `src/main.rs` — разбор аргументов на `clap`. Команд две: `--version` и `mcp`. Без аргументов печатается справка. Ошибка `swhy mcp` даёт код выхода 3.
- `tests/cli.rs` — запускает собранный бинарь как дочерний процесс. Проверяет точный вывод `--version` и диалог с `swhy mcp` по двум версиям протокола.

### `crates/swhy-mcp` — MCP-сервер

- `src/lib.rs` — сервер на `rmcp` поверх stdio. `get_info` переопределён, поэтому сервер представляется как `swhy`, а не `rmcp`. Инструментов нет: на `tools/list` приходит `{"tools": []}`. Четыре инструмента из ТЗ добавит E14.
- В stdout идёт только JSON-RPC. В крейте нет ни одного `println!`.
- `run_stdio()` создаёт tokio-runtime и обслуживает соединение, пока клиент его не закроет. Эту функцию и вызывает `swhy mcp`.

### `fixtures/` — тестовые git-репозитории

Алгоритмам истории нужны репозитории с заранее известной историей и постоянными SHA. Этот каталог их производит.

| Путь | Для чего |
| --- | --- |
| `lib.sh` | функции для скриптов: `fx_init`, `fx_write`, `fx_commit`, а также `fx_mv`, `fx_rm`, `fx_branch`, `fx_checkout`, `fx_merge` |
| `fx-smoke.sh` | 6 коммитов; задействует каждую функцию `lib.sh`. Нужен только тестам самого фреймворка |
| `fx-rename.sh` | 7 коммитов: переименование метода, смена меток аргументов, вынос метода в extension в другом файле, перегрузки, merge. Заготовлен под тесты E4 |
| `src/lib.rs` | Rust-хелпер `fixtures::build(name) -> PathBuf` и функции чтения репозитория: `head_sha`, `commit_shas`, `refs`, `git` |
| `src/main.rs` | бинарь `swhy-fixtures` с командами `list` и `build` |
| `tests/framework.rs` | 15 тестов фреймворка |

Пакет называется `swhy-fixtures`, а библиотека в нём — `fixtures`, чтобы в тестах писать `fixtures::build(...)`, как в ТЗ (ADR-1).

**Как получаются одинаковые SHA.** SHA коммита зависит от автора, почты, дат и содержимого. `lib.sh` фиксирует всё, кроме содержимого:

- автор и коммиттер — всегда `Fixture Author <fixture@swhy.test>`;
- дату каждого коммита задаёт скрипт вторым аргументом `fx_commit`, она идёт и в `GIT_AUTHOR_DATE`, и в `GIT_COMMITTER_DATE`; дата без явного смещения (`+00:00`) отклоняется;
- настройки git с машины отключены: глобальный и системный конфиг заменены на `/dev/null`, подпись коммитов выключена, `TZ=UTC`, `LC_ALL=C`.

**Как работает `fixtures::build`.** Репозиторий собирается в `target/fixtures/<имя>` один раз за прогон тестов:

1. Внутри одного процесса путь запоминается в памяти, повторный вызов возвращает его сразу.
2. Между процессами сборку защищает блокировка файла `target/fixtures/<имя>.lock`.
3. Рядом лежит штамп `target/fixtures/<имя>.stamp`. В нём идентификатор прогона и хеш скриптов (`lib.sh` и `fx-<имя>.sh`). Если штамп совпал — репозиторий берётся готовым, иначе удаляется и собирается заново.
4. Идентификатор прогона — PID родительского процесса, то есть того `cargo test`, который запустил тестовые бинари. Его можно задать явно переменной `SWHY_FIXTURES_RUN_ID`.

Тест не должен менять репозиторий, который вернул `build`: его делят все тесты прогона. Для личной копии есть `fixtures::build_fresh(name, dest)`.

**Как добавить fixture.** Создать `fixtures/fx-<имя>.sh`, который принимает каталог назначения в `$1`, подключает `lib.sh` и вызывает функции `fx_*`. Имя — строчные латинские буквы, цифры и дефисы после `fx-`. Регистрировать его нигде не нужно: `fixtures::names()` находит скрипты по маске.

### `crates/swhy-eval` и `eval/` — замеры

Правило ТЗ: каждая метрика считается скриптом из `eval/`, запускается одной командой и пишет JSON в `eval/results/`.

- `crates/swhy-eval` — бинарь `swhy-eval`, в котором живёт логика замеров. Сейчас в нём одна команда: `fixture-determinism`.
- `eval/e0.sh` — обёртка в одну команду: запускает `swhy-eval fixture-determinism --builds 2`.
- `eval/results/E0-2026-11-14.json` — результат: 2 fixture из 2 идентичны за две сборки.

Команда собирает каждый fixture дважды с нуля во временный каталог `target/fixtures/.eval/` и сравнивает HEAD, SHA всех коммитов и все refs. Код выхода 0, если всё совпало, иначе 1.

В файле результата четыре обязательных поля — `head_sha`, `command`, `params`, `metrics` — и `worktree_dirty`: были ли незакоммиченные изменения в момент замера. Времени генерации в файле нет, поэтому два запуска на одном коммите дают побайтово одинаковый файл.

### `app/` — приложение

- `app/src-tauri` — крейт `swhy-app`. Зависит от `swhy-core` и возвращает его версию. Зависимости `tauri` и команд приложения ещё нет (ADR-4).
- `app/ui` — заготовка интерфейса: `package.json` с закреплёнными версиями CodeMirror, Vite и TypeScript, `index.html` и `src/main.ts` с одной строкой текста.

Приложение появится на E15. Сейчас это только место в структуре.

## CI

`.github/workflows/ci.yml` запускается на каждый push и pull request, на `macos-latest`. Шаги: установка toolchain из `rust-toolchain.toml`, затем `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test --workspace`. Повторный push в ту же ветку отменяет незавершённый прогон.

## Что не сделано и что стоит знать

- **`app/ui` не собирался.** На машине разработки нет Node и npm; версии пакетов сверены только с реестром npm.
- **Сборка на Rust 1.89 не запускалась.** Проверено только, что ни один внешний пакет из `Cargo.lock` не требует версии выше.
- **Расхождения ТЗ с crates.io для будущих этапов** (ADR-5): `tree-sitter` 0.27.2 и `tauri` 2.12.5 требуют Rust 1.90 при заявленном в ТЗ 1.89; у `reqwest` 0.13.5 нет фичи `rustls-tls`, есть `rustls`.
- **Приёмка.** Проверяющий подтвердил 29 пунктов из 30. Пункт «CI зелёный» он проверить не смог: на машине нет `gh`. Зелёный прогон подтвердил пользователь, этап принят его решением — это записано в `docs/reviews/E0.md`.
