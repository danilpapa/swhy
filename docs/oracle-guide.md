# Руководство по разметке эталонов

Правила разметки эталона истории методов и построчного эталона (E1). Разделы E9 (пары ObjC → Swift) и E11 (цепочки регрессий) заполняются на своих этапах.

## Эталон истории методов (E1)

### Состав

ТЗ, E1: 50 методов, у каждого не меньше 3 изменяющих коммитов; не меньше 10 с переездом между модулями и не меньше 10 с ObjC-происхождением. По решению от 2026-11-14 все 50 методов — из Signal-iOS, ревизия закреплена в `eval/repos.toml`.

- **Метод** — объявление `func` с телом в Swift-файле закреплённой ревизии. `init`, `subscript`, вычисляемые свойства и требования протоколов в эталон не входят.
- **Изменяющий коммит** — коммит, после которого текст метода или его место (файл, ключ) отличаются от родителя. Коммит появления считается отдельно: условие «не меньше 3» проверяется по коммитам кроме него.
- **Модуль** в Signal-iOS — каталог верхнего уровня (`Signal`, `SignalServiceKit`, `SignalMessaging`, `SignalUI`, …): он соответствует таргету Xcode. Переезд внутри одного каталога верхнего уровня (`SignalServiceKit/src/X.swift` → `SignalServiceKit/X.swift`) — переезд файла, не модуля.
- **ObjC-происхождение** — в истории метода есть коммит, до которого метод был методом Objective-C.

### Отбор методов

1. `swhy-eval oracle-pool` берёт случайную выборку методов закреплённой ревизии (зерно в параметрах команды) и для каждого запускает `git log -L :<func>:<file>`. Не берутся пути тестов, сгенерированный и сторонний код (`Tests/`, `/test/`, `/Generated/`, `ThirdParty/`, `*.pb.swift`).
2. Кандидат годится, если в его истории `git log -L` от 4 до 15 коммитов и метод не длиннее 80 строк. Границы сверху — чтобы каждый коммит можно было проверить вручную.
3. Методы берутся в порядке выборки, по слоям: сначала с обрывом истории на удалённом ObjC-файле, затем с переездом между каталогами верхнего уровня, затем остальные.
4. Метод отклоняется после ручной проверки, если изменяющих коммитов меньше 3 или текст метода не извлекается однозначно (два объявления с одним ключом в файле). Вместо него берётся следующий из того же слоя. Отклонённые методы и причины — в `eval/oracle/rejected.tsv`.

### Разбиение

25 методов — `train` (подбор порогов), 25 — `test` (проверка). Внутри каждого слоя методы чередуются в порядке отбора. Проверочную часть не использовать для подбора порогов, весов и параметров и не смотреть до E17.

### Кандидаты

Для каждого метода `swhy-eval oracle-sheet` собирает объединение:

- `git log --follow -M -- <file>` — все коммиты файла;
- `git log -L <start>,<end>:<file>` — коммиты диапазона строк метода;
- merge-коммиты, задевающие файл (`git log --merges --full-history`);
- текущая версия инструмента — на E1 история в `swhy` ещё не реализована, источник пуст (`candidates.tool = 0`); добавляется при пересборке эталона после E4.

Текст метода в коммите и в родителе извлекается лексическим сканером (`crates/swhy-eval/src/scan.rs`): от комментариев и атрибутов прямо над объявлением до закрывающей скобки. Строка `// MARK` и пустая строка отделяют комментарий от метода.

- Текст и путь совпадают — коммит метод не менял и в лист проверки не попадает.
- Текст или путь отличаются — коммит попадает в лист проверки с дифом метода.
- Метода до коммита нет — сканер предлагает происхождение: метод, исчезнувший из того же файла (переименование), из другого файла, изменённого или удалённого этим коммитом (переезд), ObjC-метод с тем же именем (переписывание). Предложение показывается разметчику вместе с обоими текстами.
- Merge-коммит сравнивается с каждым родителем. Он попадает в лист, только если текст метода отличается от всех родителей.

### Ручная проверка

Разметчик читает каждый пункт листа проверки и решает:

1. Изменил ли коммит метод. Если нет (изменилась соседняя строка, попавшая в диапазон) — `NotChanging`.
2. Класс изменения — один, самый сильный из применимых (порядок силы: `Semantic`, `Refactoring`, `SignatureChanged: attributes`, `RenameOnly`, `DocOnly`, `FormatOnly`, `MoveOnly`).
3. Верно ли предложенное происхождение. Если предложенный предшественник — другой метод (совпало только имя, тело написано заново для другой задачи), трасса обрезается на этом коммите, и он становится коммитом появления.

### Классы изменения

| Класс | Когда ставится |
| --- | --- |
| `Introduced` | Коммит появления: до него метода нет и предшественник не найден |
| `FormatOnly` | Отличаются только пробелы, переносы строк и обычные комментарии (`//`, `/* */`) |
| `DocOnly` | Изменился только doc-комментарий (`///`, `/** */`) над методом или внутри него |
| `RenameOnly` | Тексты совпадают после согласованного переименования: самого метода, его меток, параметров, локальных переменных. Переименование вызываемого метода или типа, объявленного в другом месте, сюда тоже относится, если больше ничего не изменилось |
| `SignatureChanged: attributes` | Изменились только атрибуты объявления: `@objc`, `@MainActor`, `@discardableResult`, `@available`, `@nonobjc` |
| `Refactoring` | Структурное преобразование без смены поведения: `if let` ↔ `guard let`, вынос выражения в локальную константу, замена явного типа выводимым, `self.` ↔ без `self`, сокращённый `if let x`, trailing closure, перевод `static func` ↔ метод без изменения логики, смена модификатора доступа (`public`, `private`) |
| `Semantic` | Всё остальное: изменилась логика, вызовы, условия, типы параметров или результата, `async`/`throws`, значения по умолчанию, сообщения в логах |
| `MoveOnly` | Изменился только путь файла или ключ контейнера, текст метода тот же |

Поле `move` ставится отдельно от класса: `file` — другой файл в том же модуле, `module` — другой каталог верхнего уровня, `cross_language` — метод переписан с Objective-C. Если коммит и перенёс метод, и изменил текст, класс берётся по изменению текста.

Переписывание ObjC → Swift всегда `Semantic` с `move = cross_language`: тексты на разных языках не сравниваются как форматирование.

### Решения, принятые заранее

ТЗ, E1, пункт 5:

- изменение doc-комментария — отдельный технический класс `DocOnly`;
- изменение атрибутов (`@MainActor`, `@objc`) — `SignatureChanged: attributes`;
- merge-коммит сравнивается с каждым родителем.

Дополнительно:

- Изменение сообщения в логе или строкового литерала — `Semantic`: каноническая форма (E6) литералы не нормализует.
- Добавление или удаление `self.` перед свойством — `Refactoring`.
- Смена модификатора доступа — `Refactoring`: поведение метода не меняется, но это не форматирование.
- `async`, `throws`, `@MainActor` в сигнатуре: атрибут `@MainActor` — `SignatureChanged: attributes`; `async` и `throws` — `Semantic`.
- Коммит, который только переносит файл (`git mv`), — `MoveOnly`.
- Коммит-откат (`Revert`) размечается как обычный коммит по своему дифу.

### Второй разметчик

Второй разметчик проверяет 30% методов — 15 из 50, их идентификаторы перечислены в `eval/oracle/second/README.md`. Он получает листы проверки (`swhy-eval oracle-sheet`) без меток первого разметчика и заполняет `eval/oracle/labels/signal-ios-second.tsv` в том же формате. Файлы `eval/oracle/second/<repo>-<n>.json` собирает `eval/oracle/build.sh`.

Каппа Коэна считается `eval/oracle/check.sh` по парам меток двух разметчиков. Объект сравнения — коммит из объединения размеченных обоими (изменяющие и `NotChanging`). Считаются две каппы: «изменил / не изменил» и по классу.

### Формат файлов

Источник разметки — `eval/oracle/labels/<repo>.tsv`, поля разделены табуляцией:

```
M	<id>	<train|test>	<путь>	<ключ>
C	<коммит>	<класс>	[примечание]
X	<коммит>
```

`M` начинает метод, `C` задаёт класс коммита, `X` обрезает трассу на коммите. Сокращения классов: `I` — `Introduced`, `F` — `FormatOnly`, `D` — `DocOnly`, `R` — `RenameOnly`, `A` — `SignatureChanged: attributes`, `X` — `Refactoring`, `S` — `Semantic`, `M` — `MoveOnly`, `N` — `NotChanging`.

`eval/oracle/build.sh` заново строит трассу каждого метода, проверяет, что у каждого пункта листа ровно одна метка, и пишет `eval/oracle/methods/<repo>-<n>.json`, схема `swhy-oracle-method/1`:

| Поле | Значение |
| --- | --- |
| `id`, `repo`, `rev` | идентификатор, репозиторий, закреплённая ревизия |
| `split` | `train` или `test` |
| `annotator` | кто размечал |
| `method`, `lines` | путь и ключ метода в `rev`, строки объявления и конца |
| `candidates` | число кандидатов по источникам: `follow`, `log_l`, `merges`, `union`, `tool` |
| `introduced` | коммит появления |
| `objc_origin`, `module_move` | признаки слоёв |
| `history` | изменяющие коммиты от старых к новым: `commit`, `date`, `parent`, `path`, `key`, `from`, `class`, `move`, `sources`, `note` |
| `not_changing` | коммиты, проверенные вручную и признанные не изменяющими |

Ключ метода — в формате ТЗ («Формат ключа символа»), построен сканером E1. После E2 ключи сверяются с разбором `swhy-core`.

## Построчный эталон (E1, неделя 10)

ТЗ: 20 методов из проверочной части, около 400 строк; у каждой строки — последний смысловой коммит.

- Строки — все непустые строки тела метода в закреплённой ревизии, кроме строк из одних скобок.
- **Последний смысловой коммит строки** — самый поздний коммит из `history` метода с классом `Semantic`, после которого текст этой строки (без учёта пробелов) впервые принял нынешний вид с точностью до изменений классов `FormatOnly`, `RenameOnly`, `Refactoring`, `MoveOnly`.
- Строка, пришедшая из ObjC-версии без смысловых изменений после переписывания, получает коммит переписывания.
- Формат: `eval/oracle/lines/<repo>-<n>.json`, для каждой строки — номер в `rev`, текст, коммит.

Разметка выполняется на неделе 10, перед E7.
