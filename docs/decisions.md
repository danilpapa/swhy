# Решения (ADR)

Сюда записывается любое решение, которого нет в `docs/TZ.md`. Формат записи:

```
## ADR-<k>. <Название> (E<n>, <дата>)

**Контекст.** Что требует ТЗ и где оно молчит или противоречит себе.
**Решение.** Что сделано.
**Отвергнутые варианты.** Что рассматривалось и почему не выбрано.
```

Записи не переписываются задним числом: если решение меняется, добавляется новая запись со ссылкой на старую.

## ADR-1. Где живёт `fixtures::build` и что входит в фреймворк fixture (E0, 2026-11-14)

**Контекст.** ТЗ (E0, шаг 3) требует «Rust-хелпер `fixtures::build("fx-rename") -> PathBuf`», но в структуре репозитория каталог `fixtures/` описан только как «скрипты fx-*.sh», а крейтов в `crates/` перечислено четыре. Имена крейтов по ТЗ — `swhy-*`. Список функций `lib.sh` в ТЗ — `fx_init`, `fx_commit`, `fx_write`; fixture `fx-rename` (E4) требует ещё ветки и merge-коммит.

**Решение.**

- Каталог `fixtures/` — одновременно каталог скриптов и пакет Cargo `swhy-fixtures` с именем библиотеки `fixtures` (`[lib] name = "fixtures"`). Вызов в тестах выглядит дословно как в ТЗ: `fixtures::build("fx-rename")`.
- У пакета есть бинарь `swhy-fixtures` (`build <name>`, `list`): он собирает fixture тем же кодом, что и тесты, и печатает путь, SHA HEAD и идентификатор сборки. Нужен, чтобы собрать fixture без написания теста, и для теста «одна сборка за прогон» между процессами.
- В `lib.sh` кроме трёх функций из ТЗ есть `fx_mv`, `fx_rm`, `fx_branch`, `fx_checkout`, `fx_merge`. Сигнатуры трёх функций из ТЗ не изменены.
- `fx_commit` принимает дату только с явным смещением (`2024-01-10T10:00:00+00:00`); `fx_write` — только относительный путь внутри репозитория. Иначе SHA зависел бы от машины.
- `lib.sh` отключает конфигурацию git машины (`GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_SYSTEM=/dev/null`), задаёт автора и почту (`Fixture Author <fixture@swhy.test>`), `TZ=UTC`, `LC_ALL=C`, выключает подпись коммитов и `autocrlf`.
- В E0 созданы два fixture: `fx-smoke` (проверяет сам фреймворк) и `fx-rename`. `fx-rename` назван в ТЗ в примере вызова хелпера, поэтому создан уже сейчас со сценарием, перечисленным в E4 (переименование, смена меток, перенос в extension в другом файле, перегрузки, merge-коммит). Ожидаемые события для него задаёт E4.

**Отвергнутые варианты.**

- Крейт `crates/swhy-fixtures`: добавляет в `crates/` пятый крейт, которого нет в структуре ТЗ, и разносит скрипты и хелпер по разным каталогам.
- Модуль `fixtures` внутри `swhy-core`: тестовый код попал бы в ядро.
- Пакет с именем `fixtures`: нарушает правило имён `swhy-*`.
- Fixture без `fx-rename` до E4: пример из ТЗ `fixtures::build("fx-rename")` не выполнялся бы.

## ADR-2. Что значит «один раз за прогон тестов» (E0, 2026-11-14)

**Контекст.** ТЗ (E0, шаг 3): хелпер «собирает репозиторий в `target/fixtures/` один раз за прогон тестов». `cargo test` запускает несколько тестовых бинарей как отдельные процессы, внутри бинаря тесты идут в потоках. ТЗ не говорит, как процессы узнают, что они — один прогон.

**Решение.**

- Прогон определяется идентификатором: значение переменной `SWHY_FIXTURES_RUN_ID`, если она задана, иначе PID родительского процесса (`cargo test` или `cargo nextest`, который запустил тестовые бинари).
- Рядом с репозиторием лежит `target/fixtures/<name>.stamp`: идентификатор прогона, хеш `lib.sh` и скрипта fixture, идентификатор сборки. Если штамп совпал — репозиторий переиспользуется, скрипт не запускается. Если прогон другой или скрипты изменились — репозиторий собирается заново.
- Между процессами сборку защищает блокировка файла `target/fixtures/<name>.lock` (`File::lock`, std, Rust 1.89), внутри процесса — мьютекс и карта уже собранных fixture.
- `fixtures::build_fresh(name, dest)` всегда собирает с нуля в указанный каталог. Им пользуются тесты детерминизма и тесты, которым нужна своя копия.

**Отвергнутые варианты.**

- Только штамп по хешу скриптов (собрать один раз и переиспользовать во всех прогонах): кеш `swhy` лежит внутри `.git` репозитория (`<git-common-dir>/swhy/cache.sqlite`), поэтому «холодные» тесты следующих этапов получали бы прогретый кеш от прошлого прогона.
- `OnceLock` в каждом тестовом бинаре без штампа: сборка столько раз, сколько тестовых бинарей, — не «один раз за прогон».
- Сборка в `build.rs`: запускается при компиляции, а не при прогоне, и не пересобирает fixture между прогонами.

**Ограничение.** Если PID родителя совпал с PID прошлого прогона (повторное использование PID системой), fixture переиспользуется. Содержимое при этом то же: штамп включает хеш скриптов.

## ADR-3. Типы модели, которые ТЗ называет, но не определяет (E0, 2026-11-14)

**Контекст.** Структура репозитория в ТЗ: «`model.rs` — типы из раздела «Термины и модель данных»». Ни один этап не содержит шага «создать модель», поэтому она создана вместе с каркасом. В блоке «Структуры (Rust)» используются типы без определения: `CommitId`, `TaskKey`, `Confidence`, `TestFramework`, `PathStep`, `Skeleton`. Формат сериализации перечислений в ТЗ не задан.

**Решение.**

- `CommitId(pub String)`, `TaskKey(pub String)` — по образцу `SymbolKey(pub String)`; все три сериализуются как простая строка.
- `Confidence { High, Medium, Low }` и `TestFramework { XCTest, SwiftTesting }` — из комментариев в блоке структур.
- `PathStep { Body, Stmt(u32), IfThen }` — ровно варианты из примера ТЗ `[Body, Stmt(3), IfThen, Stmt(0)]`. Остальные варианты добавляет E2 (якоря операторов).
- `Skeleton` — поля по списку из E9, шаг 4: `selectors`, `string_literals`, `numbers`, `words` (мешок слов со счётчиками), `types`, `param_count`, `control: ControlShape { ifs, fors, switches, returns }`. Множества — `BTreeSet`, мешок — `BTreeMap`: порядок детерминирован, типы остаются `Eq + Hash`.
- Перечисления сериализуются в `snake_case`, как в примере ответа `swhy/1` (`"bugfix"`, `"body_changed"`, `"guarding"`, `"medium"`); `Lang` — `"swift"` / `"objc"`, как префикс ключа символа; `ObjCMethod` — `"objc_method"`, `XCTest` — `"xctest"`. Варианты с полями — внешне тегированные (`{"renamed": {"from": "…"}}`), потому что кеш разборов по ТЗ хранится в bincode, а bincode не поддерживает внутренне тегированные перечисления serde.
- Сами структуры перенесены из ТЗ без изменений состава и порядка полей. Подтипы `SignatureChanged`, пометка `extracted_from`, событие `MovedToExtension` (E4) в E0 не добавлялись.

**Отвергнутые варианты.**

- Пустой `model.rs` до E2: структура ТЗ прямо называет его содержимое.
- `Skeleton` и `PathStep` как пустые заглушки: `SymbolSnapshot` и `Anchor` тогда нельзя проверить round-trip-тестом с осмысленными данными.
- `CommitId` как `[u8; 20]`: в ответе и в примерах ТЗ коммиты — строки (`"4f2e1aa"`), а SHA-256-репозитории дали бы другую длину.

## ADR-4. Что в каркасе — заготовка, а что работает (E0, 2026-11-14)

**Контекст.** ТЗ (E0, шаг 1): «Создать workspace по структуре из раздела «Архитектура и стек»». Структура перечисляет файлы, которые наполняются на этапах E2–E15. Приложение описано как «Tauri: `src-tauri/` (зависит от swhy-core) + `ui/` (TypeScript, Vite, CodeMirror 6)».

**Решение.**

- Все каталоги и файлы структуры созданы. Модули `swhy-core`, кроме `model.rs`, — пустые файлы с указанием этапа; `todo!()` и `unimplemented!()` не используются, потому что функций в них ещё нет.
- Зависимость добавляется в `[workspace.dependencies]` на том этапе, который первым её использует, с точной версией из таблицы ТЗ (`=4.6.7`, `=3.9.0`, …). В E0 это `clap`, `rmcp`, `serde`, `serde_json`, `tokio`.
- `app/src-tauri` — пакет `swhy-app`, член workspace, зависит от `swhy-core`. Зависимость `tauri`, `tauri.conf.json` и команды добавляет E15: приложение Tauri собирается вместе с UI, для этого нужны шаги Node, которых нет среди трёх команд CI из ТЗ и которые нельзя проверить на машине разработки (см. «Ограничение»).
- `app/ui` — `package.json` с версиями из таблицы ТЗ (`@codemirror/view` 6.43.15, `@tauri-apps/api` 2.12.4, `@tauri-apps/cli` 2.12.4), `tsconfig.json`, `index.html`, `src/main.ts`. Версии `@codemirror/state` 6.7.6, `@codemirror/legacy-modes` 6.5.5, `typescript` 7.0.2, `vite` 8.3.8 — последние в реестре npm на 2026-11-14.

**Отвергнутые варианты.**

- Полное приложение Tauri уже в E0: это работа E15, и собрать его без Node нельзя.
- Объявить все зависимости таблицы сразу: неиспользуемые записи не попадают в `Cargo.lock`, их версии и фичи остались бы непроверенными сборкой.
- `app/src-tauri` вне workspace: его код не проверялся бы тремя командами CI.

**Ограничение.** На машине разработки нет Node и npm, поэтому `app/ui` не устанавливался и не собирался. Проверено только, что версии пакетов существуют в реестре npm.

## ADR-5. Версия Rust и расхождения в таблице зависимостей (E0, 2026-11-14)

**Контекст.** ТЗ: «Rust stable (версия закреплена в `rust-toolchain.toml`)», `rust-version = "1.89"`, «Сверить версии зависимостей в `Cargo.lock` с docs.rs». Конкретную версию stable ТЗ не называет.

**Решение.**

- `rust-toolchain.toml`: `channel = "1.94.1"`, компоненты `rustfmt`, `clippy`. Это stable, установленный на машине разработки; `rust-version = "1.89"` в `[workspace.package]` остаётся нижней границей.
- Сборка на Rust 1.89 в E0 не запускалась. Проверено по `cargo metadata`: ни один из 106 внешних пакетов `Cargo.lock` не объявляет `rust-version` выше 1.89.
- `rmcp-macros` закреплён в `Cargo.lock` на 3.9.0 (`cargo update -p rmcp-macros --precise 3.9.0`), чтобы совпадать с `rmcp` 3.9.0.

**Расхождения ТЗ с crates.io, найденные при сверке версий (не решались в E0, решает указанный этап):**

| Что в ТЗ | Что на crates.io | Кто решает |
| --- | --- | --- |
| `rust-version = "1.89"` и `tree-sitter` 0.27.2 | `tree-sitter` 0.27.2 объявляет `rust-version = 1.90` | E2 |
| `rust-version = "1.89"` и `tauri` 2.12.5 | `tauri` 2.12.5 объявляет `rust-version = 1.90` | E15 |
| `reqwest` 0.13.5 с фичей `rustls-tls` | у 0.13.5 такой фичи нет, есть `rustls` | E8 |

Все версии из таблицы «Зависимости» существуют на crates.io (проверено `cargo info <крейт>@<версия>` 2026-11-14).

**Отвергнутые варианты.**

- `channel = "stable"`: версия не закреплена, CI и разработчик могли бы собирать разными компиляторами.
- `channel = "1.89"`: это нижняя граница, а не рабочая версия; с ней `tree-sitter` 0.27.2 не соберётся уже на E2.
- Поднять `rust-version` до 1.90 сейчас: ТЗ прямо задаёт 1.89, а зависимости E0 его не нарушают.

## ADR-6. Запись критерия E0 через `eval/` (E0, 2026-11-14)

**Контекст.** У E0 нет метрик в смысле ТЗ, есть критерий «`fixtures::build` дважды даёт одинаковые SHA». Постоянное правило: «Каждая метрика считается скриптом из `eval/`… и пишет результат в `eval/results/<этап>-<дата>.json`».

**Решение.** Критерий проверяется тестами (`fixtures/tests/framework.rs`) и дополнительно записывается скриптом `eval/e0.sh`: каждый fixture собирается дважды с нуля, сравниваются SHA всех коммитов и refs, результат — в `eval/results/E0-<дата>.json` с полями `head_sha`, `command`, `params`, `metrics`. В файле есть также `worktree_dirty`: были ли незакоммиченные изменения в момент замера. Времени генерации в файле нет.

**Отвергнутые варианты.** Не писать файл результата для E0: проверяющему пришлось бы верить выводу тестов без записанного `head_sha`.

## ADR-7. Что закоммичено из исходного состояния репозитория и где идёт работа (E0, 2026-11-14)

**Контекст.** До E0 в репозитории был один коммит (`.gitignore`), а `docs/TZ.md`, `.claude/agents/`, `skills/` и `data/` лежали неотслеживаемыми. Правило исполнителя: в конце этапа `git status --porcelain` пуст. ТЗ (E1): репозитории датасета «клонировать полностью в `data/repos/`, в git не коммитить».

**Решение.**

- `docs/TZ.md`, `.claude/agents/*.md`, `skills/swhy-observer/SKILL.md` закоммичены без изменений содержимого.
- `data/repos/` добавлен в `.gitignore`. Содержимое каталога не трогалось.
- Коммиты этапа сделаны в ветке `dev`, а не в `main`. `git push` не выполнялся.

**Отвергнутые варианты.**

- Добавить `.claude/` и `skills/` в `.gitignore`: определения агентов и навыка — часть процесса работы по ТЗ и должны версионироваться вместе с ним.
- Коммитить прямо в `main`: вернуть ветку по умолчанию в исходное состояние сложнее, чем влить `dev`.

**Следствие.** Критерий «CI зелёный» в E0 проверен только локально теми же тремя командами. Запуск на GitHub Actions требует `git push`, который исполнитель не делает.

## ADR-8. Имена файлов результатов E1 (E1, 2026-11-15)

**Контекст.** Постоянное правило ТЗ: метрика пишется в `eval/results/<этап>-<дата>.json`. Критерий приёмки E1 называет другой файл: «`eval/results/E1-measure.json` с цифрами пунктов 1–4».

**Решение.** Замер проблемы пишется в `eval/results/E1-measure.json` (команда `eval/measure/run.sh`) — так, как назван в критерии. Проверка эталона и каппа пишутся в `eval/results/E1-<дата>.json` (команда `eval/oracle/check.sh`) — по постоянному правилу. В обоих файлах поля `head_sha`, `worktree_dirty`, `command`, `params`, `metrics`, без времени генерации.

**Отвергнутые варианты.** Один файл `E1-<дата>.json` для всего: критерий приёмки прямо называет `E1-measure.json`. Два файла с датой: то же.

## ADR-9. Определения замера проблемы (E1, 2026-11-15)

**Контекст.** ТЗ (E1, «Замер проблемы») задаёт четыре замера одной-двумя фразами каждый. Ниже — всё, что пришлось доопределить, чтобы цифры были воспроизводимы.

**Решение.**

- **Ревизия.** Все цифры считаются на коммите из `eval/repos.toml`, а не на том, что сейчас выгружено в клоне. Конфигурация git машины отключена (`GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_SYSTEM=/dev/null`), версия git записана в `params.git_version`. Клон только читается (`GIT_OPTIONAL_LOCKS=0`).
- **Выборки.** Генератор SplitMix64, зерно в `params.seed`. Если выборка не меньше совокупности, берётся вся совокупность.
- **Пункт 1.** «Коммиты» — все коммиты, достижимые из закреплённой ревизии; merge-коммиты посчитаны отдельно. «Годы» — по дате коммиттера. Файлы ObjC — расширения `.h`, `.m`, `.mm`. «Изменение больше 1000 файлов» — число путей в `git log --name-only --no-renames`; у merge-коммита собственных изменений нет, он в этот список не попадает.
- **Пункт 2.** 500 строк выбираются равновероятно из всех строк всех `.swift` закреплённой ревизии, включая пустые (их число в выборке записано в `sampled_blank_lines`). Blame запускается по файлу целиком, а не с `-L n,n`: `-M` и `-C` оценивают блоки строк, одна строка почти никогда не набирает порог в 20 и 40 символов. «Изменение только пробелов» проверяется для файла: `git diff -w <previous>:<путь> <коммит>:<путь>` пуст, где `previous` — из вывода `git blame --line-porcelain`. «Массовый коммит» — больше 200 путей по определению пункта 1.
- **Пункт 3.** В git 2.46 нет встроенного драйвера `diff` для Swift, а правило по умолчанию (строка начинается с буквы в первой колонке) не находит метод с отступом: `git log -L :reset:Core/Math.swift` на fixture падает с «no match» (тест `item_3_stock_git_cannot_address_an_indented_swift_method`). Поэтому замер задаёт `diff.swift.xfuncname` (значение в `params.swift_xfuncname`) через `-c` и файл атрибутов вне репозитория. `<func>` — регулярное выражение `func[ \t][ \t]*<имя>[ \t]*[(<]`. Совокупность — объявления `func` с именем-идентификатором, по одному на пару (файл, имя): `-L :<func>:<file>` берёт первое совпадение в файле. «История заканчивается на коммите, где файл добавлен» — у последнего коммита истории диф начинается с `--- /dev/null`. «Удалён файл с методом того же имени» — среди файлов, удалённых этим коммитом (`git diff-tree --diff-filter=D --no-renames`), есть `.swift` с `func <имя>` или `.h`/`.m`/`.mm` с методом, у которого первый кусок селектора равен имени.
- **Пункт 4.** Ключевые слова — список слабых сигналов из E8 ТЗ, без изменений. Слово засчитывается, если стоит в начале слова сообщения, без учёта регистра (`fix` находит `Fixes`, не находит `prefix`). База доли — коммиты без merge-коммитов. Основная цифра — по сообщению целиком, рядом — только по первой строке и число коммитов на каждое слово.

**Отвергнутые варианты.**

- `git blame -L n,n` на одну строку: быстрее на порядок, но для режима `-M -C -C` это другой замер.
- Запускать `git log -L :<func>:<file>` без `xfuncname`: все 200 историй закончились бы ошибкой, доля обрывов не определена.
- Выбрасывать пустые строки из выборки пункта 2: ТЗ говорит «случайных строк Swift».
- Свой список ключевых слов для пункта 4: в ТЗ есть готовый.

**Следствие.** Под `git blame -w` коммит, изменивший в файле только пробелы, не может быть автором строки по построению, поэтому слагаемое «только пробелы» в пункте 2 ожидаемо близко к нулю; технический шум в этом замере дают массовые коммиты.

## ADR-10. Лексический сканер в `swhy-eval` вместо разбора (E1, 2026-11-15)

**Контекст.** E1 идёт «до появления инструмента»: разбор Swift и ObjC появляется в E2. Замеру нужен список методов ревизии, а эталону — текст метода в произвольном коммите.

**Решение.** В `crates/swhy-eval/src/scan.rs` — лексический сканер: комментарии и строковые литералы заменяются пробелами, объявления ищутся по ключевому слову `func` и по знаку `-`/`+` в начале строки, тело — по парным скобкам. Ключ метода строится в формате ТЗ. Сканер живёт в `swhy-eval`, а не в `swhy-core`, и `tree-sitter` не использует: эталон не должен строиться кодом, который потом по нему оценивается.

**Отвергнутые варианты.** Подключить `tree-sitter` уже в E1: это работа E2, и эталон зависел бы от оцениваемого разбора. Регулярные выражения по строкам без учёта комментариев и литералов: `func` внутри строки или комментария давал бы ложные методы.

**Ограничения.** Сканер не понимает `#if` с двумя реализациями одного метода (берётся первая), regex-литералы Swift, методы ObjC внутри `namespace { }` в `.mm`.

## ADR-11. Устройство эталона истории методов (E1, 2026-11-15)

**Контекст.** ТЗ (E1, «Эталон истории методов») задаёт состав, источники кандидатов и классы, но не задаёт: что такое модуль в репозитории без SPM, считать ли коммит появления изменяющим, как отбирать методы, схему файла.

**Решение.**

- **Модуль** в Signal-iOS — каталог верхнего уровня (таргет Xcode). Правило E5 «`<X>/Sources/<Module>/` или каталог с `*.xcodeproj`» здесь даёт один модуль на весь репозиторий: `Signal.xcodeproj` лежит в корне.
- **«Не меньше 3 изменяющих коммитов»** проверяется без коммита появления — более строгое из двух прочтений.
- **Отбор:** случайная выборка, слои, границы (история `git log -L` от 4 до 15 коммитов, метод не длиннее 80 строк), исключённые пути — в `docs/oracle-guide.md`.
- **Классы.** К классам ТЗ (`FormatOnly`, `RenameOnly`, `Refactoring`, `Semantic`, переезд, `DocOnly`, `SignatureChanged: attributes`) добавлены `Introduced` (коммит появления), `MoveOnly` (переезд без правки текста) и `NotChanging` (кандидат проверен и отклонён). Переезд записывается отдельным полем `move`, чтобы коммит «переезд + правка» имел и класс, и переезд.
- **Границы классов** взяты из определений E6, чтобы разметку можно было сравнивать с классификатором: запись, которую каноническая форма считает одинаковой (висячая запятая, явный `self.`, неявный `return`), — `FormatOnly`; `RenameOnly` — только собственное имя метода, метки, параметры и локальные переменные; переименование вызываемого метода или типа — `Semantic` с примечанием `external rename only`. Смена модификатора доступа и `static` ↔ метод экземпляра отнесены к `Refactoring`: ТЗ их класс не называет.
- **Источник «текущая версия инструмента»** на E1 пуст: история в `swhy` появляется в E4. В файле метода это видно как `candidates.tool = 0`.
- **Merge-коммит** сравнивается с каждым родителем и считается изменяющим, только если текст метода отличается от всех родителей.
- **Источник разметки** — `eval/oracle/labels/<repo>.tsv`; JSON-файлы `eval/oracle/methods/<repo>-<n>.json` собираются из него командой `eval/oracle/build.sh`, которая заново строит трассу и требует метку для каждого её шага.

**Замена метода.** Из первых 50 отобранных один метод отклонён после ручной проверки (`eval/oracle/rejected.tsv`): предложенный ObjC-предшественник оказался одноимённым методом другого класса, а без него изменяющих коммитов два. На его место встал следующий годный метод слоя.

**Отвергнутые варианты.** Модуль по правилу E5: ни одного переезда между модулями в Signal-iOS не нашлось бы. Считать коммит появления изменяющим: методы с двумя правками проходили бы порог. Писать JSON руками: 50 файлов с полными SHA без проверки на соответствие истории.

## ADR-12. Кто размечает эталон (E1, 2026-11-15)

**Контекст.** ТЗ: «Затем ручная проверка каждого коммита», «Второй разметчик проверяет 30% методов; посчитать каппу Коэна». ТЗ адресовано агенту и не говорит, кто первый и кто второй разметчик.

**Решение.** Первый разметчик — исполнитель этапа (агент); в каждом файле это записано в поле `annotator`. Он прочитал лист проверки каждого метода и поставил класс каждому коммиту по правилам `docs/oracle-guide.md`. Второй разметчик должен быть независим от первого, поэтому исполнитель его роль не выполняет: повторный проход той же моделью по тем же листам не даёт независимой оценки, и каппа по нему ничего бы не измеряла. Для второго разметчика подготовлено: список 15 методов (`eval/oracle/second/README.md`), листы проверки (`eval/oracle/sheet.sh`), формат меток, сборка и подсчёт каппы (`eval/oracle/check.sh`).

**Отвергнутые варианты.** Разметить те же 15 методов второй раз самому и посчитать каппу: число получилось бы, но требование ТЗ о втором разметчике не было бы выполнено. Не размечать вовсе до появления двух людей: критерий «50 размеченных методов» остался бы невыполненным целиком.

**Следствие.** Критерий приёмки «каппа посчитана» в E1 не выполнен, пока нет разметки второго разметчика. `eval/oracle/check.sh` при этом завершается с кодом 1 и пишет причину в `metrics.violations`.

## ADR-13. Зависимость `toml` (E1, 2026-11-15)

**Контекст.** `eval/repos.toml` требуется ТЗ; в таблице зависимостей ТЗ крейта для TOML нет, хотя конфиг `.swhy.toml` тоже в этом формате.

**Решение.** `toml = "=1.2.1"` (последняя версия на crates.io на 2026-11-15) в `[workspace.dependencies]`, используется в `swhy-eval`.

**Отвергнутые варианты.** Свой разбор трёх строк `ключ = "значение"`: молча принял бы файл с ошибкой формата.
